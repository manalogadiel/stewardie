# Private pilot: account deletion and report operations

Status: operator procedure and local tool are implemented. One disposable live account was processed successfully on September 28, 2026. This is not a published retention policy or proof of public-release readiness. The external deletion page remains unpublished.

## What the cleanup does

The account owner requests deletion in Account Settings or, once published, through the external page. The request is stored privately at `deletionRequests/{uid}`. The founder-only review sheet can see it but cannot mark it complete. The local operator tool requires the exact UID and an existing request, starts in dry-run mode, and needs separate `--apply --confirm-uid <uid>` flags (`--live` too for the real project). It never runs in the app or scheduled worker.

The tool refuses to proceed if the account owns a space with other members. Transfer ownership in Stewardie first; this requires the recipient to accept. A space owned only by the deleting account is removed recursively. For other spaces, access and live location are revoked before media cleanup, the account's mood/check-in, plan, routine, moment/reaction, and arrival records are removed, and shared tasks are kept without that person's UID or activity name. Historical records in spaces the member already left are scanned too; completion and live-sharing recipient attribution are cleared. Active tasks they owned/requested become unclaimed. Shared task text remains for coordination; requests to redact sensitive text need manual review. This is a pilot technical choice, subject to privacy-policy review before public release.

Supabase photo objects are removed through the Storage API before their `media_items` rows are deleted. The tool also removes the person's quota rows and clears their `completed_by` attribution on other uploaders' photos. Remaining objects under the affected Storage prefixes stop completion for manual review. Firebase account subcollections, invitations, relevant reports and blocks, and Auth identity are removed. The request record is deleted last, after cross-service checks. A partial failure leaves `needsAttention` in the private queue; check whether Auth disabling and space-access revocation succeeded before retrying. Stored space IDs let a retry resume after membership removal. Do not mark the request complete manually.

Google Play requires deletion of associated account data and a working in-app and external request path; any legitimate retention exception must be disclosed in the eventual policy. [Google Play account deletion](https://support.google.com/googleplay/android-developer/answer/13327111). Firestore document deletion alone does not remove subcollections; the tool uses recursive deletion. [Firebase deletion guidance](https://firebase.google.com/docs/firestore/manage-data/delete-data). Storage objects must be removed through the Storage API, not a SQL row deletion. [Supabase Storage guidance](https://supabase.com/docs/guides/storage/management/delete-objects).

## Operator runbook

1. Confirm the requester UID and email in the private queue and Firebase Auth. Check owned spaces and any unresolved safety issue. Never use the founder/operator account as a deletion test. Transfer shared-space ownership before proceeding. Keep secrets and service-account files outside Git.
2. In a private terminal with Firebase Application Default Credentials authorized for **Firebase Auth administration and Firestore**, set `SUPABASE_URL=https://ulexhxfxatzlobabitpr.supabase.co` and `SUPABASE_SERVICE_ROLE_KEY` from the existing Supabase project. Do not paste the key into source, a command argument, chat, or logs. From the repository root, install the checked-in backend dependencies if needed with `npm ci --prefix backend/firebase/functions`.
3. Run a dry run: `node backend/firebase/functions/scripts/process-account-deletion.mjs --project stewardie --uid <exact-uid>`. It prints only counts and blockers. Check that the space/photo counts match the operator queue and dashboard.
4. When the target is confirmed, run `node backend/firebase/functions/scripts/process-account-deletion.mjs --project stewardie --uid <exact-uid> --apply --confirm-uid <exact-uid> --live`. This irreversibly removes data. Do not use `--apply` on an actual account merely to test the tool.
5. Verify Auth lookup fails; the account document and request are gone; all affected spaces no longer list the UID; Supabase `media_items` and private Storage have no objects for that uploader; other members can still see permitted shared tasks with “Former member” attribution. Record only an anonymized completion date/count in the private support log. If the request says `needsAttention`, inspect the failure and rerun only after correcting it.

The first live test used a disposable verified account in two shared spaces. The dry run initially blocked cleanup because the account owned a space with other members; ownership was offered to and accepted by another member, then the dry run reported two shared spaces, zero solo spaces, and four photos. With the owner's explicit approval, the live processor returned `Cleanup verified` with those counts. Independent dashboard checks showed the Auth user and account/request records absent, both spaces retained with the former member removed, zero matching `media_items` rows and Storage objects, and a shared task retained with `creatorUid: deleted-account`. The account's email and UID are intentionally omitted from this document. Solo-space removal and partial-failure retry have emulator coverage but have not been exercised against live services; the test did not establish physical-device sign-in behavior or a full retention-policy review. Do not intentionally interrupt a live deletion to reproduce failure handling.

Before public release, review edge cases with the final privacy policy: legacy dependent profiles, previously deleted/orphaned spaces, local drafts and downloaded photos on devices, shared text that identifies the requester, closed reports, provider backups/log retention, and any paid entitlement or RevenueCat identity. Do not claim those are automatically erased by this tool.

## Report handling during the pilot

The founder account is the initial named operator. Check the private report queue at least once each day during an active pilot; aim to acknowledge a report within two working days. These are internal operating targets, not published guarantees. The reporter can hide a moment for themselves; blocking prevents new direct task requests. “Reviewing” means investigation started. Close as **no action needed** only after review, or **action completed** only after the separate action is actually finished. Closing a report does not delete content or remove a member. Keep report IDs and decisions in the private queue during the pilot; define and implement a retention schedule before a public release. If a report involves an account-deletion target, the cleanup tool deletes that report rather than claiming to preserve evidence under an undefined exception.

For suspected serious harm, stop access using the existing space-owner removal controls where appropriate, preserve only the minimum evidence needed for the chosen response, and record the decision privately. Do not put sensitive report text or precise location in ordinary logs.
