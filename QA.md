### 1. Critical Functional Bugs & System Crashes (Showstoppers)

#### 1.1. App Crash on Calendar/Plans in Today Screen
* **Location**: [`online_today_extras.dart:368-369`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/online_today_extras.dart#L368-L369) & [`firebase_repository.dart:440, 449-450`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/firebase_repository.dart#L440)
* **What happens**:
  ```dart
  DateTime get start => (data['startAt'] as Timestamp).toDate();
  DateTime get end => (data['endAt'] as Timestamp).toDate();
  ```
  In [`spark_backend.dart:230-231`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/spark_backend.dart#L230-L231) and [`firestore.rules:189-192`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L189-L192), plans are saved and strictly validated using integer milliseconds: `startMillis` and `endMillis`. `startAt` and `endAt` are not in the document.
* **Impact**: If any space member creates a plan on the calendar, `data['startAt']` is null. Casting null to `Timestamp` immediately crashes the screen with `type 'Null' is not a subtype of type 'Timestamp' in type cast`.

#### 1.2. Check-Ins / Moods Blocked by Security Rules (Always Fails)
* **Location**: [`spark_backend.dart:210-218`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/spark_backend.dart#L210-L218) vs [`firestore.rules:168-171`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L168-L171)
* **What happens**:
  [`firestore.rules`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L168-L171) requires:
  ```firestore
  request.resource.data.uid == uid &&
  request.resource.data.note is string && request.resource.data.note.size() <= 180
  ```
  However, `spark_backend.dart` writes:
  ```dart
  await space(id!).collection('checkIns').doc(uid).set({
    'mood': v['mood'],
    'color': v['color'],
    'updatedAt': FieldValue.serverTimestamp(),
    'expiresAt': ...
  });
  ```
  It completely omits both the `'uid'` field and the `'note'` field.
* **Impact**: Setting or updating your mood check-in in online mode will always be rejected by Firestore with `permission-denied`.

#### 1.3. Expired Plus Subscriptions Lock Users Out of Completed Task History
* **Location**: [`spark_backend.dart:177-178`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/spark_backend.dart#L177-L178) vs [`firestore.rules:10-15, 126`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L126)
* **What happens**:
  - `spark_backend.dart` checks `accountData['tier'] == 'plus'`. If a user previously had Plus, but it expired, `tier` may still say `'plus'` before webhook reconciliation completes.
  - As a result, the client omits the 3-day query filter (`completedAt >= 3 days ago`).
  - But [`firestore.rules:126`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L126) evaluates `plus()` which strictly checks `subscriptionExpiresAt > request.time`. Since it is expired, `plus()` returns false.
* **Impact**: Firestore denies the query constraint with `permission-denied`, crashing the Done tab and leaving the user with a blank list and a perpetual connection error.

#### 1.4. Type Mismatch Between Supabase Edge Function & Firestore Rules for Expiration
* **Location**: [`supabase/functions/reconcile-subscription/index.ts:137, 480`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/supabase/functions/reconcile-subscription/index.ts#L137) vs [`firestore.rules:14`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L14)
* **What happens**:
  The edge function writes `subscriptionExpiresAt` as an ISO string (`stringValue`). However, [`firestore.rules:14`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules#L14) compares it as a timestamp: `d.subscriptionExpiresAt > request.time`.
* **Impact**: In Firestore Security Rules, comparing a string to a timestamp evaluates to false or fails rule evaluation. Non-founder Plus subscribers who purchase a subscription can have their access rejected by Firestore rules even though the purchase succeeded.

#### 1.5. Crash on Invalid or Expired Invite Code

### 2. User Flow & Business Logic Flaws

* **Location**: [`online_home.dart:364-374`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/online_home.dart#L364-L374) & [`spark_backend.dart:176-207`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/spark_backend.dart#L176-L207)

However, `spark_backend.dart` ignores `personUid` in its `listCompletedTasks` query, and [`online_home.dart`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/online_home.dart#L374) renders `[...firstPage, ..._moreDone]` without filtering.
* **Impact**: The Done tab always shows everyone's completed tasks, even when a single family member is selected.

#### 2.2. Space Owners Cannot Leave or Delete Their Own Space
* **Location**: [`spark_backend.dart:326-327`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/spark_backend.dart#L326-L327) & [`firestore.rules`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/backend/firebase/firestore.rules)
* **What happens**:
  In `leaveSpace`:
  ```dart
  if (parent['ownerUid'] == target)
    throw StateError('Transfer ownership before leaving this space.');
  ```
  There is no "Delete Space" or "Archive Space" feature. If a user is the sole member of a space, they cannot transfer ownership because nobody else exists in the space, and they cannot leave.
* **Impact**: Basic tier accounts have a hard quota of 3 owned spaces. Once a user creates 3 spaces, they can never leave or delete them, permanently locking them out of creating new spaces.

* **Location**: [`photo_composer.dart:821-824`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/features/media/photo_composer.dart#L821-L824)

* **Impact**: The modal pops right back up immediately. The user is trapped in an annoying prompt loop until they figure out they must tap "Cancel" specifically on the bottom sheet.

### 3. UI / UX & Performance Issues

#### 3.1. Sequential Thumbnail Downloads + Destructive Error Handling in Moments
* **Location**: [`cloud_media_library.dart:163-177, 184`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/cloud_media_library.dart#L163-L177)
* **What happens**:
  In `refresh()`, every photo in `data['items']` calls `await _decode(...)`, which executes a sequential HTTP POST request for each thumbnail one-by-one. If a space has 15 photos, it triggers 16 sequential network requests.
  Furthermore, if *any single thumbnail* request fails due to a network stutter, the `catch` block runs:
  ```dart
  _remote.removeWhere((_, p) => p.spaceId == spaceId);
  ```
* **Impact**: Moments takes 10–20 seconds to refresh on mobile data. Because Moments auto-refreshes every 20 seconds, any small network timeout wipes all loaded photos off the screen and replaces them with an error message.

#### 3.2. Lack of Full-Photo Caching
* **Location**: [`cloud_media_library.dart:279-288`](file:///c:/Users/HP%20LAPTOP%2015s/stewardie/lib/online/cloud_media_library.dart#L279-L288)
* **What happens**:
  `fullPhoto()` downloads the full-resolution image every single time it is viewed, without keeping a local in-memory or disk cache.
* **Impact**: Repeatedly opening photos burns Supabase free-tier egress bandwidth and creates noticeable loading spinners for the user.
